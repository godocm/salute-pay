INTEGRATION GUIDE

Signed orders.
Verified receipts.

Connect merchant-owned payment links to your app using the publisher API and signed webhooks. This infrastructure never signs custody transactions.

Test environments only until deployments are verified and activated. The API is same-origin and authenticated with a wallet session. Database credentials and webhook secrets belong on your server, never in browser code.

1. Create, publish, pay, collect

  1. Merchant connects the appropriate wallet: EVM browser wallet / WalletConnect, Solana Wallet Standard, or TronLink.
  2. Merchant signs order terms off-chain. EVM uses EIP-712; Solana uses an Ed25519 message; TRON uses TIP-712.
  3. The signed order is verified and published. Its separate /pay/{slug} page carries the QR code, unique address, invoice amount and network.
  4. The customer funds the address from a wallet or exchange. For SPL tokens, the merchant prepares the token-account address before sharing it.
  5. An executor connects their own wallet, reviews payout terms and collects. Funds reach the immutable merchant, minus an authorized per-sweep reward.
  6. The watcher verifies chain receipts and sends webhooks. Do not fulfil an invoice from a browser-submitted transaction hash alone.

Repeated deposits remain collectable. Each sweep can pay the fixed reward. A zero reward or an explicit waiver performs only the merchant payout; the executor still pays network costs. A merchant can sponsor collection by executing it with their own wallet.

2. Publisher API

Fetch /api/networks for activated deployments. Authenticate using a wallet-signed challenge. The session cookie is HttpOnly and same-origin; write requests require the app origin.

GET /api/networks

Activated public deployment metadata; no wallet keys or private RPC credentials.

POST /api/auth/challenge

Send {chain,address}; receive {id,message}. Sign the exact message with your wallet.

POST /api/auth/verify

Send {id,signature}. Receives a 12-hour merchant session cookie. Challenges expire after 5 minutes and are single-use.

GET /api/me

Merchant plan, monthly usage, webhook URL and signing secret. Authenticated merchant only.

PUT /api/settings

Send {webhookUrl}. A public HTTPS hostname is required. Send an empty URL to disable delivery.

POST /api/payments

Send signed payment JSON exported from the app. Server verifies authorization, deployment and address; monthly dashboard limits are enforced atomically.

GET /api/payments

Authenticated merchant payment list.

GET /api/payments/{slug}

Public signed payment data, cumulative invoice-asset amounts and collection receipts. Anyone holding the link can view it.

GET /api/public-orders

Only orders the merchant elected to publish to executors.

POST /api/payments/{slug}/transactions

Send {chain,hash}. This queues chain verification; it never marks a payment as paid by itself.

POST /api/auth/logout

Revoke the current session.

3. Webhook delivery

Connect your wallet in Developer settings, sign in, save a webhook URL and copy its signing secret into your server environment. New payments send events only when you choose “Send webhook events” at creation. Delivery uses the saved endpoint at each attempt, including retries; changing the URL does not enable events for existing orders.

  • payment.created: verified signed order published.
  • payment.partially_paid: new confirmed invoice-asset funds bring cumulative received below the invoice amount.
  • payment.paid: confirmed cumulative invoice-asset funds meet or exceed the invoice amount.
  • payment.overpaid: confirmed cumulative invoice-asset funds exceed the invoice. The paid event is also emitted for compatibility.
  • payment.collected: confirmed collection, including actual chain, actual asset, merchant receipt and executor reward.

Underpayment, overpayment and repeated deposits do not change the merchant destination. Wrong-chain/wrong-token collections produce receipts but do not automatically satisfy the original invoice. A paid event reports customer funding, not necessarily completed merchant collection.

Deliveries are at least once. Deduplicate salute-event-id. The worker retries failures with backoff up to eight attempts; only 2xx responses acknowledge delivery. Redirects are not followed. An authenticated scheduler must invoke the watcher and sender; no long-running worker is assumed inside Vercel.

Verify the exact raw body

import { createHmac, timingSafeEqual } from "node:crypto";
// requestBody must be the original raw UTF-8 body, before JSON parsing.

if (a.length !== b.length || !timingSafeEqual(a, b)) {

4. Contract workflow

The main EVM factory uses reviewed OpenZeppelin clone and signature primitives. The deterministic address binds immutable order terms. Any executor can deploy and forward only after funding. Deployment, merchant payment and reward payment succeed together or revert together. There is no owner, admin, upgrade hook or payout setter in the EVM contracts.

The factory exposes predictAddress, verifyOrder, settle, collect and collectWithReward. Reward quotes bind the actual execution chain, asset, order digest, single-use nonce, deadline and minimum merchant receipt. They cannot change the funded deposit address or merchant.

Tempo has no native-payment path and checks exact TIP-20 recipient balances. Solana verifies the preceding Ed25519 instruction and uses immutable merchant-bound order accounts and PDAs. Classic SPL setup consumes account rent. TRON uses a dedicated TVM/TIP-712 factory and requires Bandwidth/Energy resources. Solana deployment authority must be revoked before making an ownerless deployment claim.

Invoice amount is an accounting expectation, not a minimum collection balance. A positive balance can be collected if it leaves a positive merchant receipt after any reward. Token freezes, fee-on-transfer, rebasing and incompatible token policies are not bypassed. Tests are not an independent security audit.

5. Cross-chain and wrong-asset recovery

Portable EVM recovery requires the same deterministic factory, initialization bytecode, salt and receiver implementation on both chains. The base EIP-712 order uses its fixed origin chain; recovery rewards use the actual execution chain. EOA merchant signatures are portable; foreign-chain ERC-1271 wallets are not supported.

Collect the actual asset with a zero-reward sponsored call, or supply a merchant-signed reward quote for that chain and asset. Recovery pays the same merchant on the chain where the asset arrived. It does not bridge, convert tokens, return funds to a customer or recover deposits from an unrelated address. Solana and TRON are separate payment rails.

Always show the intended network prominently. Exchange withdrawal addresses cannot be assumed to be valid customer refund destinations. Customer refunds need a separate verified merchant process and are not implemented by collection.
